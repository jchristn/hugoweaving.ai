Why Agent Smith

Your production stack lives in a dozen tabs.

An outage rarely stays in one system. You read logs in one console, query the database in another, SSH into a host, check the cluster, and piece the story together yourself at two in the morning. Agents are good at exactly this kind of cross-system detective work. The hard part has always been letting them in safely.

Agents can't see your systems

A chat assistant can explain what CLOSE_WAIT means. It can't tell you that web-01 is full of them right now. Without real connections, the agent is guessing and you're still the one doing the work.

Credentials end up in the wrong places

Wiring tools together by hand usually means pasting connection strings into config files, environment variables and, eventually, prompts. Once a password is in a transcript, you no longer control where it goes.

All or nothing access

Give an agent a shell and it can read a log file or drop a table with equal ease. Telling it "please be careful" in the system prompt is a hope, not a control.

Agent Smith is the missing layer between your agent and your infrastructure. You connect each system once, store its credentials encrypted, and decide per agent what it may read, what it may change, and what needs a human to say yes. The model never sees a secret, and policy is enforced by the server rather than by the model's good manners.

How It Works

Connect once. Compose agents. Talk from anywhere.

Everything in Agent Smith is built from three pieces: resources, secrets and agent profiles. Configure them in the dashboard's setup wizard, through the REST API, or with an SDK.

1

Add your resources

Pick a connector, point it at a target (an SSH host, a PostgreSQL server, an S3 bucket, a Kubernetes cluster) and run Test Connection. A resource is configured once and can be shared by many agents.

2

Vault the credentials

Passwords, keys and tokens go into an encrypted vault and are bound to the resource's secret slots. They resolve at execution time, so they are never part of a tool argument or a prompt.

3

Build an agent profile

Choose a model, then bind resources with an alias and an access mode: prod-db as ReadOnly, web-01 as ReadWriteWithApproval. Add instructions and runbooks the agent should follow.

4

Put it to work

Chat in the dashboard, publish a standalone chat page, or connect Claude Code, your own app or another agent over MCP, A2A, REST, the SDKs or the OpenAI-compatible API.

Safety Model

The server decides. Not the model.

Every tool call is classified as Read, Write or Destructive before it runs. A SELECT is Read, an UPDATE is Write, a DROP or a service restart is Destructive, and anything Agent Smith can't parse is treated conservatively. The binding's access mode then decides what happens.

Effect ReadOnly ReadWriteWithApproval ReadWrite
Read Allowed Allowed Allowed
Write Denied Approval Allowed
Destructive Denied Approval Approvalunless disabled for the binding

Resource ceilings, deny patterns, tool rules, tenant lockdown and credential scopes can narrow access further. Pair them with least-privilege credentials on the target systems.

Approvals with a paper trail

A call that needs approval pauses with the exact arguments, the resource and the reason. Approve or reject it with a note; the agent is told either way, and the decision lands in the audit log.

Secrets stay in the vault

Connector credentials are encrypted at rest and resolved at execution time. A scrubber runs over prompts, logs, request history, audit descriptions and tool output.

Multi-tenant by design

Every query filters by tenant. Roles, scoped credentials and profile-locked access keys control who can use which agent, and a lockdown switch freezes a tenant when you need it.

One pipeline for every surface

Dashboard, MCP, A2A, REST and the OpenAI-compatible API all go through the same invocation pipeline. There's no side door that skips classification or approval.

Benefits

Built for the people who carry the pager.

Agent Smith isn't a chatbot bolted onto a dashboard. It's an operations server that happens to speak every agent protocol worth speaking.

Faster answers during incidents

The agent checks logs, the database and the host in parallel and comes back with a diagnosis, not a list of things for you to go look at.

It learns your environment

Agents record what they discover about each resource (paths, services, tables, relationships) and reload it next time. Attach runbooks and log formats as versioned documents.

Different agents for different jobs

An on-call agent with approval-gated write access. A read-only analytics agent for the data team. A public support bot with a single HTTP API. Same resources, different bindings.

Works with the agent you already use

Point Claude Code, Cursor or Codex at the MCP endpoint and they get your resources as tools, with Agent Smith's approvals still in force. Your model, your loop, our guardrails.

Observable from day one

The Compose stack includes Prometheus, Loki, Tempo and Grafana. Every invocation, request and approval is recorded, and chat answers can be rated and reviewed.

Yours to run

MIT licensed and self-hosted on Docker Compose, Kubernetes (Kustomize or Helm) or minikube. SQLite out of the box, PostgreSQL when you want it, images for amd64 and arm64.

Use Cases

What people hand to Agent Smith.

Incident response

"Why is checkout slow?"

The agent searches the checkout logs, looks at live database activity and checks host load, then tells you which of the three is actually the problem. If the fix is a restart, it asks first.

Database work

"Which customers churned last quarter?"

SQL connectors infer schemas and relationships and keep what they learn, so a read-only agent can answer analytics questions without anyone writing the joins by hand.

Kubernetes

"The payments pods keep restarting."

Pull pod logs and events, find the OOM kill, and propose a rollout restart that waits in the approvals queue until someone on the team signs off.

Cloud inventory

"What's running in us-east-1?"

Describe EC2 instances, run CloudWatch Logs Insights queries and summarize what you're paying for, using an IAM role scoped to read.

Developer tooling

Give your coding agent production context

Connect Claude Code over MCP with a credential locked to one profile. It can read staging logs and query the dev database while you debug, and nothing more.

Agent networks

Delegate to specialists

Expose an Agent Smith profile over A2A so other agents can call it, or attach remote A2A agents and MCP servers so Agent Smith can hand work to them.

Self-service

A status page that answers questions

Publish a standalone chat link with your logo, authenticated or public, backed by a scoped credential and a read-only health check binding.

Data protection

Encrypt without exposing keys

The cryptography connector encrypts, decrypts and hashes with vault-held AES keys. The agent does the transformation; it never learns the key.

Connect

Every surface, one server port.

MCP clients bring their own model and loop. Dashboard chat, standalone chat, A2A and the OpenAI-compatible endpoint run Agent Smith's hosted loop with the profile's configured model.

Add Agent Smith to Claude Code
$ claude mcp add --transport http hugo http://127.0.0.1:8800/mcp \
    --header "x-access-key: $HUGO_ACCESS_KEY" \
    --header "x-secret-key: $HUGO_SECRET_KEY"

Create a credential in Access > Credentials and enable Lock to profile. The client receives that profile's compiled instructions, resource-scoped tools and document catalog. Stdio-only clients can use hugo mcp stdio.

The model name is the agent profile
$ curl -s -X POST http://127.0.0.1:8800/v1.0/openai/v1/chat/completions \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d '{"model": "Hugo", "messages": [{"role": "user", "content": "What tables are in demo-db?"}]}'

Any OpenAI-compatible client works. Agent Smith runs its own tools, streams in OpenAI's chunk format, and tells you in the response when a call is waiting for approval.

Bind a resource to a new agent profile
from hugo_sdk import HugoClient

with HugoClient("http://127.0.0.1:8800") as client:
    client.login("anderson@hugo.local", "password")
    secret = client.secrets.create({"name": "web-01-key", "kind": "Password", "values": {"password": "..."}})
    resource = client.resources.create({
        "name": "web-01", "connectorType": "ssh",
        "settings": {"host": "web-01.example.com", "port": 22, "username": "deploy",
                     "authMethod": "Password"},
        "secretBindings": [{"slotName": "password", "secretId": secret.id}],
    })
    profile = client.agent_profiles.create({"name": "ops", "displayName": "Ops"})
    client.agent_profiles.create_binding(profile.id, {
        "resourceId": resource.id,
        "alias": "web-01",
        "accessMode": "ReadWriteWithApproval",
    })

SDKs are available for C# (Hugo.Sdk), Python (hugo-sdk) and JavaScript/TypeScript (@jchristn/hugo-sdk), each with examples and a test harness.

Fetch a profile's agent card
$ curl -s http://127.0.0.1:8800/v1.0/a2a/default/Hugo/.well-known/agent-card.json

Each profile is an A2A agent at /v1.0/a2a/{tenantId}/{profileName}, with an agent card describing its skills. Other agents send it tasks; the same access modes and approvals apply.

Get Started

Running in about five minutes.

All you need is Docker with Docker Compose. The start script creates your .env, generates keys, and brings up the server, dashboard and observability stack.

1

Clone and start

$ git clone https://github.com/jchristn/AgentSmith.git
$ cd AgentSmith/docker
$ ./start.sh

On Windows, run start.bat. Back up docker/.env with your database: it holds the master key that decrypts the vault.

2

Sign in to the dashboard

Open http://127.0.0.1:8801 and sign in to tenant default as anderson@hugo.local with password password. Change it before anyone else can reach the stack.

3

Follow the setup wizard

Add a model endpoint (Ollama or a hosted provider with tool calling), create a secret, add a resource and test it, then bind it to an agent.

4

Say hello to Agent Smith

Open Chat and ask about your systems. Tool calls appear inline with their effect, and risky ones wait for you.
